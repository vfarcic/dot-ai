The `manageOrgData` capabilities `list` operation is now a dependable machine-readable contract, and the server exposes a real readiness signal. Listing no longer caps silently at a low limit: `limit` defaults to 10 for interactive callers but accepts up to 10000 so a consumer (such as `dot-ai-controller`) can retrieve the whole set in one call, and every response reports `totalCount`, `returnedCount`, `limit`, and an explicit `truncated` flag so a consumer computing a diff can tell a partial list from a complete one. A new `identityOnly` flag projects each item to just its `id` and `resourceName`, keeping the payload proportional to the number of resources. `totalCount` is now obtained through a cheap count instead of listing every record. The response shape is pinned by published golden fixtures under `contracts/capabilities/`, so it cannot drift without a deliberate update. Separately, a new unauthenticated `GET /readyz` endpoint verifies the capability subsystem (vector DB reachable and collection accessible) and returns `503` when it is not ready, so a subsystem outage removes the pod from the Service rotation without restarting it; liveness continues to use the always-200 `GET /healthz`.
