The `manageOrgData` capabilities `list` operation is now a dependable machine-readable contract, and the server exposes a real readiness signal. Listing no longer caps silently at a low limit: `limit` defaults to 10 for interactive callers but accepts up to 10000 so a consumer (such as `dot-ai-controller`) can retrieve the whole set in one call, and every response reports `totalCount`, `returnedCount`, `limit`, and an explicit `truncated` flag so a consumer computing a diff can tell a partial list from a complete one. A new `identityOnly` flag projects each item to just its `id` and `resourceName`, keeping the payload proportional to the number of resources. `totalCount` is now obtained through a cheap count instead of listing every record, and `truncated` is derived from `returnedCount < totalCount` so it can never contradict the counters it ships beside. `limit` is now validated as an integer (a non-integer such as `10.5` is rejected rather than silently coerced). The response shape is pinned by published golden fixtures under `contracts/capabilities/`, so it cannot drift without a deliberate update. Separately, a new unauthenticated `GET /readyz` endpoint reports whether the pod can serve a capability scan and returns `503` when it cannot, so a subsystem outage removes the pod from the Service rotation without restarting it. A pod is ready when the vector DB is reachable and — only in semantic mode (`embeddingsRequired`) — embeddings actually serve, so an embedding or TEI model that is still unavailable independently produces a `503` even while the vector DB is up. Collection existence and `storedCount` are reported but informational: an absent collection is a healthy fresh-install state and never makes the pod not-ready, and a keyword-only deployment is ready without any embedding backend. Liveness continues to use the always-200 `GET /healthz`.
